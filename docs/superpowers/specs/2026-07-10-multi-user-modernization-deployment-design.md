# ZGCA 多用户现代化升级与生产部署设计

日期：2026-07-10  
状态：已批准进入实施  
目标分支：`codex/multi-user-modernization`

## 1. 背景与已确认决策

ZGCA Workbench 当前是可运行的单用户学习管理系统，核心功能、SQLite 数据层、文件存储、认证、Dockerfile、基础响应式布局和备份脚本均已存在。升级不重写业务，而是在保留现有能力的基础上完成多用户隔离、Admin 管理、现代化界面和生产部署。

已确认的产品决策：

- 使用北京腾讯云轻量应用服务器，Ubuntu Server 24.04 LTS，4 核 4GB，40GB SSD，3Mbps 公网带宽。
- 正式入口为 `https://zgca.zhuorui.me`。
- 使用国内直连方案：Cloudflare 仅管理 DNS，Caddy 提供 HTTPS 和反向代理。
- 面向不超过 10 位受邀用户，不开放公众注册。
- 每位普通用户有独立学习数据；Admin 可管理账号并查看或修改所有用户数据。
- 用户本人同时拥有一个普通账号；Admin 是分离的管理账号。
- SQLite 继续作为主数据库，上传文件继续落本地持久化存储。
- Windows 笔记本和 Mac mini 用于开发；Mac mini 不再承担正式公网服务，并作为异地备份节点。
- 采用小批次、可回滚的 Git 提交；最终交付升级简报、验证证据和部署手册。

## 2. 目标与非目标

### 2.1 目标

1. 在数据库、仓储层、Server Actions、API 路由和文件下载层实现严格的用户数据隔离。
2. 提供邀请制账号生命周期和独立 Admin 管理后台。
3. 保留并迁移现有学习数据，不丢失历史文件和关联关系。
4. 重构视觉系统、应用外壳和主要页面，提升桌面与移动端的信息层级、可读性和操作效率。
5. 建立统一的加载、成功、失败、空状态、确认、撤销和权限反馈。
6. 完成生产容器、域名、HTTPS、端口、备份和恢复设计。
7. 以自动化测试、响应式截图和构建结果作为阶段验收依据。

### 2.2 非目标

- 第一版不开放公开注册、社交关系、公开内容广场或用户间实时协作。
- 第一版不做离线写入和多端冲突合并；设备在线时访问服务器唯一数据源。
- 第一版不更换 PostgreSQL、不引入 Kubernetes、不做多实例部署。
- 第一版不接入付费、短信、邮件服务或第三方 OAuth。
- 第一版不把 Cloudflare Tunnel 作为正式 Web 入口。

## 3. 总体架构

访问路径：

```text
电脑 / 手机 / 平板 / 朋友浏览器
  -> zgca.zhuorui.me（Cloudflare DNS only）
  -> 腾讯云公网 IP 82.157.141.186
  -> Caddy（80/443、HTTPS、安全头、请求限制）
  -> Docker 内部网络
  -> Next.js 16 应用（仅容器内部 3000）
  -> SQLite/WAL + workspace 文件目录
```

发布路径：

```text
Windows 或 Mac 开发与测试
  -> GitHub 仓库
  -> 服务器拉取固定提交
  -> Docker Compose 构建并切换
  -> 持久化 data/backups 卷不随发布覆盖
```

Mac mini 的职责变为开发与异地备份，不参与线上请求处理。手机和平板只作为 Web 客户端，不保存业务数据库副本。

## 4. 多用户领域模型

### 4.1 账号

`users` 增加：

- `role`: `admin | user`
- `status`: `invited | active | suspended`
- `last_login_at`
- `password_changed_at`
- `must_change_password`

账号状态规则：

- `invited` 只能使用有效邀请链接设置密码。
- `active` 可正常登录。
- `suspended` 不可登录，且现有会话立即失效；数据继续保留。
- Admin 账号不用于日常学习，不自动拥有个人学习空间。

### 4.2 个人空间

新增 `workspaces`：

- `id`
- `owner_user_id`，唯一且引用普通用户
- `display_name`
- `storage_quota_bytes`
- `created_at` / `updated_at`

每位普通用户恰好拥有一个 workspace。以下业务数据全部增加 `workspace_id`：

- 科目、章节、知识点、知识标签
- 每日条目、任务、随笔草稿、学习记录
- 复习事件、错题、设置和倒计时
- 文件夹、资料元数据、资料标签与关联关系
- 统计所依赖的所有事实表

日期、科目代码、文件夹路径和标签名称等现有全局唯一键改为 workspace 内唯一。外键必须在同一 workspace 内闭合，禁止跨 workspace 关联。

### 4.3 仓储与授权边界

普通业务仓储函数不再只接收 `db`，而是接收服务端构造的作用域上下文：

```ts
type WorkspaceContext = {
  actorUserId: string;
  actorRole: "admin" | "user";
  workspaceId: string;
};
```

规则：

- 普通用户的 `workspaceId` 只能由服务端 Session 映射获得，不能信任表单、查询参数或客户端 JSON 中的用户 ID。
- Admin 选择目标 workspace 时经过独立的 `requireAdmin` 授权入口。
- 每个仓储查询显式包含 `workspace_id = ?`；禁止提供无作用域的业务查询函数。
- API 文件流先校验资料元数据属于可访问 workspace，再解析物理文件。
- Server Actions、Route Handlers 和页面加载共享同一套授权服务。

SQLite 不提供行级安全，因此自动化的双用户隔离测试是发布硬门槛。

### 4.4 文件隔离与额度

文件存储布局：

```text
data/uploads/<workspace-id>/<year>/<month>/<day>/...
```

第一版默认：

- 每位用户 2GB 总额度，可由 Admin 调整。
- 单文件最大 20MB。
- 下载必须经过认证路由，不暴露真实磁盘路径。
- 删除资料时只删除当前 workspace 的元数据和文件。
- 文件名、MIME、大小和存储键在服务端校验。

## 5. 邀请、登录与 Admin

### 5.1 邀请流程

1. Admin 输入邮箱和显示名称。
2. 系统创建 `invited` 用户并生成 24 小时有效的单次邀请令牌。
3. 数据库只保存令牌 SHA-256 哈希，不保存明文。
4. Admin 复制邀请链接并通过微信等方式发送，不依赖邮件服务。
5. 受邀用户设置密码后，令牌失效，账号转为 `active`，并创建个人 workspace 与默认知识地图。

Admin 可重新生成邀请、停用账号、恢复账号、重置密码和注销该用户全部会话。

### 5.2 Session 与登录安全

- 保留 HttpOnly、Secure、SameSite=Lax Cookie。
- Session 默认 30 天，数据库保存哈希而非原始令牌。
- 登录成功更新 `last_login_at` 和 `last_seen_at`。
- 连续失败登录受速率限制；首版按 IP 提示和邮箱组合限制。
- 用户可查看并注销自己的设备会话。
- 停用用户、重置密码或 Admin 执行“退出全部设备”时删除全部 Session。

### 5.3 Admin 后台

新增路由：

- `/admin`：用户、存储和系统概览
- `/admin/users`：用户列表、筛选和邀请
- `/admin/users/[id]`：账号状态、会话、配额、学习概览
- `/admin/users/[id]/workspace`：以管理模式查看或修改用户工作区
- `/admin/audit`：管理操作日志

Admin 修改普通用户内容时写入 `audit_logs`，至少记录操作者、目标用户、动作、实体类型、实体 ID、时间和变更摘要。敏感字段、密码和 Session 令牌不得进入日志。

## 6. 老数据迁移

迁移过程必须增量、可重复检测且不破坏历史数据：

1. 部署前生成 SQLite 一致性快照和上传目录副本。
2. 现有唯一用户继续作为普通用户，现有密码保留。
3. 为该用户创建 legacy workspace，将所有现有业务数据和文件归属到该 workspace。
4. 新增独立 Admin：首次部署通过 `APP_ADMIN_EMAIL` 与高强度 `APP_ADMIN_PASSWORD` 创建，Admin 邮箱必须与普通用户不同。该密码只用于首次登录，`must_change_password` 强制管理员立即修改；修改成功后从服务器环境文件移除 `APP_ADMIN_PASSWORD`。
5. 重建包含全局主键或唯一约束的表，改为 workspace 内唯一。
6. 校验迁移前后每张表的记录数、文件数、引用完整性和关键统计。
7. 迁移完成前不删除旧列或旧文件；验证通过后再由后续版本清理兼容结构。

## 7. 前端与交互设计

### 7.1 设计原则

视觉定位是“安静、现代、信息密度适中的学习操作系统”：

- 行动优先于装饰性统计。
- 层级依靠排版、留白和分组，不依赖大量同权重卡片。
- 桌面高效、移动端原生感、触控区域不小于 44px。
- 状态颜色只表达状态，不用颜色替代文字。
- 支持键盘、明显焦点、减少动态效果和基础 WCAG 对比度。

### 7.2 设计系统

建立语义令牌：

- 背景、表面、边框、主文字、次文字、强调色
- success / warning / danger / info
- 8px 间距体系、字体比例、圆角、阴影和层级
- light / dark / system 主题

CSS 拆分为：

- `globals.css`：重置、字体、设计令牌和全局可访问性规则
- 应用外壳与共享原语的 CSS Module
- 领域组件自己的 CSS Module
- 第三方 FullCalendar 覆写单独隔离

不引入重量级组件库；复用 React、Lucide 与原生 CSS，保持可控体积和一致性。

### 7.3 应用外壳

- 桌面：可折叠侧栏、上下文标题栏、主内容区。
- 平板：窄侧栏或抽屉导航。
- 手机：四个核心底部导航项 + “更多”；快速记录使用明确的主操作。
- 收纳面板从永久右栏改为按需抽屉。
- 用户菜单提供账号、设备会话、主题和退出。
- Admin 导航与普通用户导航分离。
- 新增 `Ctrl/Cmd + K` 命令菜单，用于导航、搜索和快速创建。

### 7.4 页面重组

首页：

- 首屏突出下一步行动、今日任务、到期复习和错题。
- 时钟与连续学习天数降级为紧凑信息。
- 科目进度突出阻塞项和待复习风险。
- 次级区域展示最近活动与七日趋势。

今日工作台：

- 任务为主区域；复习、错题和资料是相关上下文。
- 日记、晚间总结和明日第一步使用分段编辑器，并持续显示自动保存状态。
- 快速记录统一为学习、错题、想法和资料四种类型。
- 移动端减少卡片堆叠，通过分段、折叠和底部抽屉降低滚动长度。

科目与知识：

- 桌面使用导航树 + 详情区；移动端逐级进入。
- 知识点支持搜索、筛选、掌握度和复习状态，不在窄屏压缩成不可读表格。

资料库：

- 统一搜索、筛选、排序、批量选择和详情抽屉。
- 文件、知识点、错题和学习记录使用一致的关联组件。

Admin：

- 使用数据表格、筛选、状态 Badge 和危险操作确认。
- 查看用户 workspace 时始终显示醒目的“管理模式”和目标用户信息。

### 7.5 统一反馈

- Skeleton：页面级和列表级加载。
- Empty State：说明原因并提供下一步动作。
- Toast：成功、失败和可撤销操作。
- Error Boundary：页面区域错误不会破坏整个应用外壳。
- 删除优先软删除或提供短时 Undo；永久删除使用二次确认。
- 表单错误显示在字段附近，并保留用户已输入内容。

## 8. 功能升级范围

首轮功能升级包括：

- 全局命令菜单和当前用户范围搜索。
- 统一快速记录入口。
- 账号邀请、状态、Session 与存储额度管理。
- Admin 用户概览、workspace 查看和审计日志。
- 用户个人资料、密码修改和设备会话管理。

## 9. 生产部署与安全

### 9.1 Docker Compose

生产 Compose 包含：

- `zgca-workbench`：不发布公网端口，仅 `expose: 3000` 给内部网络。
- `caddy`：发布 80/443，挂载 Caddyfile，并持久化 `/data` 与 `/config` 以保存证书。
- `data`、`backups` 为宿主机持久化目录。

Next.js 继续单实例运行。镜像改为 standalone 输出并使用非 root 用户，降低镜像体积和运行权限。

### 9.2 DNS 与 HTTPS

- 完成 ICP 备案后，将 `zgca.zhuorui.me` 改为 A 记录指向 `82.157.141.186`，DNS only。
- Caddyfile 使用正式域名并反向代理到应用容器。
- 验证 HTTPS、自动续期、HTTP 到 HTTPS 跳转和安全 Cookie。
- 新入口验证通过后再移除旧 `zgca-workbench` Tunnel 连接配置。

### 9.3 端口与 SSH

- 云防火墙只开放 80、443 和受控的 22。
- 删除公网 3000 端口映射并关闭云防火墙 3000 规则。
- 为 Windows 和 Mac 分别创建 SSH 密钥；验证密钥登录后关闭密码登录。
- 禁止 root SSH 登录；保留 Ubuntu 普通用户和 sudo。
- `ssh.zhuorui.me` 保持 DNS only。

## 10. 备份与恢复

### 10.1 备份内容

- SQLite 使用在线备份 API生成一致性快照。
- 上传目录与数据库快照属于同一备份批次。
- 记录备份清单、数据库校验结果、文件数和总大小。

### 10.2 保留策略

- 每日 7 份
- 每周 4 份
- 每月 12 份

服务器保留本地副本；Mac mini 使用计划任务经 SSH 拉取备份作为异地副本。传输使用 SSH，加密磁盘使用 FileVault。备份成功与失败写入日志，Admin 可查看最近备份状态。

### 10.3 恢复演练

每月至少执行一次临时目录恢复：

1. 恢复数据库和上传目录。
2. 使用临时端口启动应用。
3. 验证登录、用户隔离、资料下载和关键统计。
4. 记录恢复时间和结果。

未经过恢复验证的备份不视为可靠备份。

## 11. 测试与质量门槛

每个阶段至少运行：

- Vitest 单元和仓储集成测试。
- Next.js 生产构建与 TypeScript 检查。
- Playwright 登录、邀请、双用户隔离、Admin、上传与核心页面冒烟。
- 390px、768/1024px、1440px 响应式审计和关键页面截图。
- 键盘导航、可见焦点、减少动态效果和 axe 基础可访问性检查。

多用户发布硬门槛：

- 用户 A 无法通过页面、Action、API 或文件 URL 读取/修改用户 B 数据。
- 普通用户无法访问 Admin 路由和操作。
- 停用用户的现有 Session 失效。
- 邀请链接过期和单次使用行为正确。
- Admin 跨用户修改写入审计日志。
- 迁移前后数据计数、文件计数和引用完整性一致。

## 12. 实施阶段与 Git 策略

阶段一：多用户基础

- 作用域数据模型、迁移、仓储上下文、邀请、角色和隔离测试。

阶段二：Admin 与账号体验

- Admin 路由、用户生命周期、Session、审计和个人设置。

阶段三：现代化界面

- 设计令牌、应用外壳、反馈原语、首页、今日、知识、资料库和 Admin 视觉迁移。

阶段四：生产化

- standalone 容器、Caddy、端口、备份、部署与恢复验证。

Git 规则：

- 功能分支为 `codex/multi-user-modernization`。
- 每个提交只包含一个可描述、可验证的逻辑变更。
- 不混入用户现有的 `docker-compose.yml` 未提交修改。
- 数据迁移、仓储隔离、Admin、设计系统、页面迁移和部署配置分别提交。
- 每次提交前运行与改动范围相称的测试；阶段结束运行全量测试和构建。

## 13. 最终验收标准

最终版必须同时满足：

1. Admin 与普通账号分离，邀请制账号流程完整。
2. 不超过 10 位用户可在任意现代浏览器独立使用自己的数据。
3. 现有数据和上传文件完整迁移到用户的普通账号。
4. 所有业务数据、文件和统计经过 workspace 隔离测试。
5. 主页、今日、科目、资料库、设置、登录和 Admin 在桌面与移动端完成现代化升级。
6. 关键交互具备加载、空状态、成功、失败、确认和撤销反馈。
7. 测试、生产构建、响应式审计和可访问性检查通过。
8. 备案完成后，正式域名通过 HTTPS 访问，3000 不暴露公网。
9. 自动备份可运行，并完成一次真实恢复演练。
10. 提供最终升级简报，包含架构、功能、视觉、迁移、部署、验证、Git 提交和剩余建议。
